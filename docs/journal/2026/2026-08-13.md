# 2026-08-13 — First real Ansible playbook, and swapping a test VM for better coverage

**Time spent:** ~2h
**Project:** projects/00-configuration-baseline/
**Related objective(s):** LO-001, LO-004

## Objective for this session
Replace the Ubuntu test VM with a Fedora one for better package-family coverage, then write and prove the first real (non-ping) Ansible playbook.

## What I did
- Verified the Ubuntu VM's disk via `domblklist`, then removed it cleanly (`virsh undefine --remove-all-storage`).
- Downloaded an official Fedora 44 Cloud Base qcow2 image, reused the leftover Ubuntu cloud-init YAML files (renamed) rather than retyping them from scratch.
- Built `fedora-test-1` the same way as the earlier two VMs, confirmed SSH access.
- Rebooted `debian-test-1`, updated `inventory.ini` to cover both Debian and Fedora VMs, confirmed connectivity to both via the ping module.
- Wrote a first real playbook (`baseline.yml`): install `htop`, plus a Debian-only conditional task to refresh the apt cache.
- Hit and diagnosed a real failure: htop wouldn't install on Debian because a fresh cloud image's apt cache was never refreshed. Fixed with a conditional task using `when: ansible_facts['os_family'] == "Debian"`.
- Learned a real limitation of `--check` (dry-run) mode: it can't fully simulate a task whose purpose is to enable a later task, since nothing actually changes during a dry run.
- Ran the playbook for real, then ran it again immediately — second run showed `changed=0`, proving idempotency directly rather than just reading about it.

## What I learned (in my own words)
_(First attempt — worth revisiting once rested.)_

The `ansible.builtin.package` module is smart about which underlying tool to use per distro (`apt` on Debian, `dnf` on Fedora), so the same task works across both without me writing separate logic — but that only works if the underlying package manager already knows about the package. A completely fresh cloud image's package index can be empty, so "install X" can fail even though X genuinely exists in the distro's repositories — the fix is refreshing the cache first, and that's a real, common first step in real configuration management, not a workaround.

I also learned dry-run mode has a real limit: it can predict "this cache update would change something," but it can't then pretend a later task can use a cache that, in the simulated world, was never actually refreshed. That's not a bug in Ansible — it's an honest boundary of what dry-run simulation can promise.

The actual proof of idempotency was seeing `changed=0` on the second identical run — not something I had to take on faith, something I directly watched happen.

## Friction / blockers
The real Debian package failure took a moment to understand — first glance it looked like Ansible was broken, but the actual cause (empty apt cache on a brand-new image) made sense once diagnosed properly. Also briefly broke `baseline.yml`'s YAML structure (missing a task-starting dash) while hand-editing it, which reinforced the earlier YAML lessons about dashes marking list items.
